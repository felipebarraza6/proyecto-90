# Migración completa de Proyecto 90 a Yggdra — borrar Express, backend 100% en Yggdra

## Resultado de la auditoría (contexto)

**Yggdra (`yggdra_infra`)**: Django 6 + DRF + Postgres, multi-tenant por `Branch` con roles configurables (`BranchRoleDefinition`), ya tiene `customers.Client` (con extra-fields dinámicos y `EMH` con peso/estatura/IMC), `employees.Employee` (1:1 con User), auth por Token DRF (`login_complete` ya devuelve `role_code` por sucursal), módulos con permisos, Docker/CI. Faltan: roles COACH/NUTRICIONISTA, serie histórica de mediciones y el dominio de coaching completo.

**Proyecto 90**: app madura (v52, Express+Vite+SQLite) que ya autentica contra Yggdra (`server/auth.ts`), pero roles en tabla local espeja, sin branch, y crear usuarios NO crea la cuenta en Yggdra. No hay datos históricos que migrar (la BD se siembra en cada arranque; nunca hubo `data/` productiva).

**Decisión del usuario**: Yggdra es dueño de TODO el dominio (futura mantención/rotabilidad); se BORRA la app Express de P90 y la SPA habla directo con Yggdra. Participantes = `Client` del branch (+ `User` tipo CL + `BranchUser`); coaches/nutricionistas = `Employee` + `User` + `BranchUser` con roles COACH/NUTRICIONISTA. El usuario de integración M2M queda innecesario (no hay backend intermedio); opcional a futuro.

## Arquitectura final

- **Yggdra**: nueva app `api/apps/coaching` (genérica, multi-branch: "Proyecto 90" es la primera sucursal) + extensiones en `customers`. Sirve además los endpoints de compatibilidad `/api/app`, `/api/files`, `/api/export` con el MISMO contrato que la SPA usa hoy, para no reescribir la capa de datos del frontend.
- **Proyecto 90**: repo queda solo como SPA (Vite+React). Login directo contra `/api/accounts/users/login_complete/`, token + `X-Branch-ID` en cada request.

## Fase 1 — Yggdra: backend completo (app `coaching` + extensión `customers`)

1. **Scaffold** `api/apps/coaching/` con la convención del repo (`models/`, `serializers/`, `views/`, `services/`, `router.py`, `tests/`, `migrations/`), registrar en `INSTALLED_APPS`, agregar módulo `coaching` en `api/apps/shared/constants/modules.py` y montar en `api/config/django/urls.py` (sin colisionar rutas existentes).
2. **Extensión de `customers`** (migración, con lo elegido de "modelos fitness nuevos"):
   - `ClientFitnessProfile`: `client` FK unique, `goal`, `activity_level`, `training_days`, `preferred_location`, `dietary_restrictions`, `motivation`, `assigned_coach` FK → `employees.Employee` (null).
   - `ClientMeasurement`: serie histórica — `client` FK, `recorded_at`, `day` (null/30/60/90), `weight_kg`, `waist_cm`, `source`, `recorded_by`, `notes` + endpoint de stats.
   - Sincronizar `EMH` (estatura/peso/IMC) al guardar perfil.
3. **Modelos de dominio** en `coaching` (todos `BranchModelApi`, portados del schema SQLite de P90): `Program`, `ProgramGuide`, `Workout`, `Exercise`, `WorkoutExercise`, `ClientEnrollment` (ex user_programs), `NutritionPlan` (macros + PDF + flujo review), `NutritionScreening` (salida del motor), `NutritionDailyLog`, `HabitDailyLog`, `Checkpoint` (día 30/60/90, reflexión/percepción, FK a `ClientMeasurement`), `IntakeQuestion`, `IntakeResponse`, `CoachingMeeting` (flujo ≥48h), `AdherenceOutreach`, `ClientProgramApproval` (ex professional_approvals), `ContentItem`, `LiveSession`, `ClientNote`, `AppMeta` (versionado de seeds). Participantes referencian `customers.Client`; profesionales referencian `employees.Employee`.
4. **Motores portados a Python**: `services/nutrition_engine.py` (Harris-Benedict, red flags TCA/medicación/cirugía bariátrica, rangos de macros, triage automatic/validation/mandatory_review — desde `db/nutrition-rules.ts`), `services/adherence.py` (40% entrenamiento / 40% macros / 20% agua), `services/bootstrap.py` (armado del JSON de arranque por rol) y `services/actions.py` (dispatcher de las ~30 acciones con chequeo de roles).
5. **Endpoints de compatibilidad SPA** en `coaching/views/`:
   - `GET /api/app` → mismo bootstrap que hoy (con `?viewAs=` de admin).
   - `POST /api/app` → dispatcher de acciones (`participant.create`, `professional.create`, `intake.submit`, `nutrition.review`, `meeting.request`, etc.). `participant.create` crea `User(CL)`+`BranchUser`+`Client`; `professional.create` crea `User`+`Employee`+`BranchUser` con rol COACH/NUTRICIONISTA (usa los endpoints/flows existentes de accounts: `create_and_assign`, `generate-password`/`set-initial-password`).
   - `POST/GET /api/files` → PDF privado (media storage) con permisos por rol/propiedad; `GET /api/export` → CSV con BOM y escape anti formula-injection.
   - Auth: Token DRF + `X-Branch-ID` (BranchMiddleware y permisos por módulo ya existen). Rol P90 se deriva de `BranchUser.role_definition.code`: `P90_ADMIN`/`OWNER`→admin, `COACH`→coach, `NUTRICIONISTA`→nutrition, `CL`→participant.
6. **Seed y roles**: management command `seed_proyecto90` (idempotente, versionado en `AppMeta`): Branch "Proyecto 90", `BranchRoleDefinition` P90_ADMIN/COACH/NUTRICIONISTA con permisos de lectura/escritura en módulos `coaching`+`customers`, `Position` Coach/Nutricionista, 4 programas + guías + ejercicios (desde `routine-guides.json` portado), ~70 preguntas de intake (desde `intake-seed.ts`), usuario admin inicial.
7. **Tests pytest** (factories por convención): aislamiento por branch, mapeo de roles, acciones del dispatcher, motor nutricional (casos red flag), regla 48h de meetings, permisos de archivos.

## Fase 2 — Proyecto 90: quedar como SPA pura

1. **Borrar**: `server/`, `worker/`, `db/access.ts`, `db/queries.ts`, `db/schema.ts`, `drizzle/`, `drizzle.config.ts`, `app/api/`, `app/page.tsx`, `app/layout.tsx`, `app/chatgpt-auth.ts`, `.next/`, `.vinext/`, `.wrangler/`, `.openai/`, `deploy/`, `README-DEPLOY.md`, `Dockerfile` (reemplazo). Antes se portan a Yggdra: `db/nutrition-rules.ts`, `db/intake-seed.ts`, `db/routine-guides.json`.
2. **package.json**: quitar `express`, `better-sqlite3`, `busboy`, `cors`, `drizzle-orm` y scripts `server:*`; queda `vite` + React + Tailwind.
3. **Auth directo a Yggdra**: `src/pages/Login.tsx` → `POST /api/accounts/users/login_complete/`; guardar token + `branch_id` + `role_code`; `src/App.tsx` usa `/api/accounts/users/me/` y `/logout/`; `authHeaders()` en `app/functional-app.tsx` agrega `X-Branch-ID`; cookie `auth_token` para descargas PDF (`CookieTokenAuthentication` ya existe en Yggdra).
4. **vite.config.ts**: proxy `/api` → `http://localhost:8000`.
5. **Dockerfile nuevo**: build estático de la SPA → nginx alpine (sirve `dist/client`).

## Fase 3 — Despliegue y validación E2E

1. Levantar Yggdra local (`docker-compose.light.yml`, API :8000), `migrate` + `seed_proyecto90`, correr pytest de la app nueva.
2. E2E con la SPA en dev: login admin → crear coach y nutricionista (nacen como Employee+User del branch con password generado) → crear participante (User CL + Client) → login participante → intake con triage del motor nutricional → asignar programa → hábitos/nutrición diaria → checkpoints 30/60/90 (peso a `ClientMeasurement`) → reunión 1:1 → subir/descargar PDF → export CSV → verificar cliente y empleados visibles en `/admin/` de Yggdra.
3. Prod: nginx de Yggdra sirve la SPA estática y proxyea `/api` (guía existente `docs/NGINX_MULTIDOMAIN.md`), configurar `CORS_ALLOWED_ORIGINS`/`custom_domain` del branch; se elimina el flujo cPanel.

## Notas y límites

- No hay migración de datos históricos (no existía data productiva).
- La SPA mantiene su contrato `/api/app`; RESTificar por recursos queda como evolución posterior opcional.
- Pagos (landing cobra $69.990 CLP) fuera de alcance; cuando toque, usar `plan_checkout`/`BranchClientSubscription` de Yggdra.
- `recipes` de Yggdra es etiquetado de recetas, no planes de macros: los planes nutricionales quedan en `coaching`.
